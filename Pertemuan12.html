Bagian I

Model Proses To-Be

Merancang Kondisi Masa Depan yang Ideal, Ramping, dan Terukur.

Definisi Konseptual

Apa itu Model "To-Be"?

  • Model **To-Be (Future State)** adalah representasi grafis alur kerja usulan perbaikan setelah penyakit operasional dibuang.
  • Bukan sekadar mimpi indah tanpa pijakan, melainkan cetak biru realistis yang memperhitungkan kapabilitas software dan SDM.
  • Menjadi dokumen acuan pengembang (*Software Requirements Specification*) bagi programmer.

Perbandingan Fundamental: As-Is vs To-Be

Model As-Is (Saat Ini)

- Cermin realita kondisi berjalan.
- Penuh aktivitas manual dan map kertas.
- Bottleneck antrean berhari-hari.
- Berfokus pada identifikasi penyakit.

Model To-Be (Usulan)

- Rancangan arsitektur yang dioptimasi.
- Alur terdigitalisasi via integrasi API.
- Waktu tunggu dipangkas hingga detik.
- Berfokus pada penciptaan nilai tambah.

Kriteria Kelayakan

3 Syarat Utama Diagram To-Be

  • **Eliminasi Bottleneck:** Titik hambatan yang terdeteksi di P10 sudah hilang atau dialihkan ke bot.
  • **Security-Aware:** Mematuhi prinsip CIA Triad dan pemisahan tugas (Segregation of Duties).
  • **Realistis Diimplementasikan:** Menggunakan teknologi yang terjangkau oleh organisasi objek.

Munculnya Lane Sistem Otomatis

Transformasi Swimlanes di To-Be

Pada diagram As-Is, hampir seluruh Lane diisi oleh manusia (Kasir, Staf Gudang, Manajer). Di diagram To-Be, sering kali muncul **Lane Baru** khusus perangkat lunak: "Payment Gateway Engine", "Portal Web Mahasiswa", atau "Notification Service" yang mengambil alih 70% beban kerja klerikal manusia.

Studi Kasus Transformasi

Contoh: Pendaftaran Kursus Bahasa

  • **As-Is:** Pendaftar isi kertas form → Staf input Excel → Validasi transfer bank via buku tabungan → Terbit kartu member 3 hari.
  • **To-Be:** Form web terintegrasi Payment Gateway → Webhook kirim bukti sukses → E-Card QR Code langsung muncul di layar HP dalam 5 detik!

"Merancang model masa depan bukan tentang menggantikan manusia dengan komputer, melainkan membebaskan manusia dari tugas membosankan agar fokus pada interaksi yang bernilai tinggi."

— Thomas H. Davenport

Bagian II

Gap Analysis

Memetakan Jurang Perbedaan Antara Masa Kini dan Masa Depan.

Metode Analisis Kesenjangan

Apa itu Gap Analysis?

  • Teknik evaluasi formal untuk mengidentifikasi **jurang pemisah (Gap)** antara kondisi riil (As-Is) dan kondisi target (To-Be).
  • Menjawab 3 pertanyaan penting: Di mana kita sekarang? Di mana kita ingin berada? Apa saja yang harus dibangun untuk sampai ke sana?

Anatomi Matriks Gap Analysis

1. As-Is Baseline

Fakta proses saat ini beserta keluhan inefisiensi yang dialami.

2. The Gap (Jurang Masalah)

Akar penyakit: Ketiadaan API, audit manual, atau format formulir kertas.

3. To-Be Target

Alur kerja baru yang diusulkan lengkap dengan notasi BPMN-nya.

4. Solusi TI & Enabler

Perangkat lunak, database, modul keamanan, atau bot yang wajib dibangun.

Format Standar Tabel Gap Analysis Laporan

ID Aktivitas As-Is Permasalahan (Gap) Pola Heuristik Rancangan To-Be Enabler TI Pendukung
GAP-01 Cek mutasi rekening kasir manual Waktu tunggu verifikasi 3 jam Task Automation Verifikasi instan via Webhook Payment Gateway API (Midtrans/Xendit)
GAP-02 Gudang menunggu nota cetak kurir Alur sekuensial lambat Parallelism Packing & cetak invoice bersamaan Parallel Gateway + Queue Server
GAP-03 Tanda tangan paraf 3 manajer Menunggu atasan cuti dinas Task Elimination Auto-Approval dana < Rp 500rb Business Rule Engine

Klasifikasi Celah

3 Dimensi Jurang Kesenjangan

  • **Technology Gap:** Belum ada software pendukung, tidak ada integrasi database, atau koneksi internet tidak stabil.
  • **Process / SOP Gap:** Aturan alur birokratis warisan masa lalu yang belum diperbarui.
  • **Skill Gap:** Operator belum terlatih mengoperasikan sistem antarmuka modern.

Keterkaitan To-Be dengan Infrastruktur TI (P6)

Kebutuhan Cloud Server

Sistem baru berbasis web membutuhkan server hosting yang memiliki fitur *auto-scaling* agar tidak crash saat panen promo.

Koneksi Failover Jaringan

Karena kasir beralih 100% digital, router toko wajib dilengkapi modem seluler 4G cadangan untuk mencegah insiden SPOF.

Database Locking

Mencegah *race condition* stok saat ribuan pengguna checkout barang promo pada detik yang bersamaan.

Keamanan Proses Baru (P7)

Security Requirement pada Model To-Be

Mengotomatisasi proses bisnis tidak boleh membuka celah baru bagi pembobolan data!

  • **Autentikasi Aman:** Terapkan Single Sign-On (SSO) dan token autentikasi API (JWT/OAuth2).
  • **Role-Based Access Control (RBAC):** Memastikan kasir hanya bisa melihat pesanan miliknya, bukan laporan laba pemilik.

Nilai Strategis Gap Analysis

Gap Analysis adalah dokumen justifikasi investasi. Tanpa tabel kesenjangan yang jelas, manajemen tidak akan mau menyetujui anggaran pembangunan sistem IT yang Anda usulkan.

Tahapan Verifikasi Gap Analysis ke Objek Observasi

  • Presentasikan Masalah As-Is: Tunjukkan data antrean dan pemborosan yang telah diverifikasi di P9 & P10.
  • Tawarkan Solusi To-Be: Jelaskan bagaimana sistem baru memangkas waktu kerja tanpa menambah beban staf.
  • Sepakati Jadwal Transisi: Pastikan pemilik usaha siap melakukan migrasi data dan pelatihan staf.

Bagian III

Notasi BPMN Solusi To-Be

Menerapkan Notasi Khusus untuk Menggambarkan Otomatisasi Sistem.

Spesifikasi Task

Beda Task Manual vs Task Otomatis

  • **User Task:** Aktivitas di mana manusia berinteraksi dengan aplikasi software (contoh: Kasir mengklik tombol konfirmasi).
  • **Service Task:** Aktivitas komputasi murni yang dieksekusi 100% oleh sistem komputer/API tanpa sentuhan manusia!

Simbol Service Task & Script Task

Service Task (Ikon Roda Gigi)

Digunakan pada diagram To-Be saat memanggil layanan cloud, memverifikasi webhook bank, atau mengirimkan payload JSON ke server logistik.

Script Task (Ikon Dokumen Kode)

Digunakan saat sistem menjalankan kalkulasi diskon otomatis, rumus pajak, atau pemformatan teks di backend.

Send/Receive Task

Digunakan untuk pertukaran pesan asinkronus (pengiriman email notifikasi otomatis atau penerimaan SMS OTP).

Komunikasi B2B

Pemodelan API via Message Flow

  • Gunakan **Message Flow (Garis Putus-Putus)** untuk merepresentasikan request HTTP POST / GET dari aplikasi toko ke server pihak ketiga (Bank/Kurir).
  • Gunakan **Message Intermediate Event** untuk menangkap respons *webhook callback* secara waktu-nyata (*real-time*).

Mengintegrasikan Single Source of Truth

Kondisi As-Is: Silo Data

Staf gudang punya catatan stok Excel sendiri, staf kasir punya buku nota sendiri. Data stok sering tidak sinkron dan memicu pembatalan pesanan.

Kondisi To-Be: Centralized Data Store

Kedua divisi dihubungkan ke simbol **Data Store (Silinder Tabung)** yang sama di cloud. Seketika kasir menjual barang, stok di gudang berkurang seketika.

Ketahanan Sistem

Boundary Timer Event (Fallback SLA)

  • Bagaimana jika pembeli tidak kunjung membayar tagihan dalam waktu 15 menit?
  • Tempelkan **Boundary Timer Event** di samping task pembayaran: jika waktu 15 menit habis, alur otomatis membatalkan pesanan dan mengembalikan stok barang!

Panduan Praktis Mengonstruksi To-Be di Draw.io

  • Duplikasi File As-Is: Jangan hapus file As-Is lama Anda. Gandakan file di Draw.io dan beri nama Proyek_Kelompok_Model_ToBe.drawio.
  • Hapus Task NVA: Lenyapkan kotak-kotak tugas manual yang telah diputuskan dibuang pada tabel Gap Analysis.
  • Sisipkan Parallel Gateway: Ganti urutan lurus dengan cabang serentak untuk aktivitas independen.
  • Tambahkan Lane Sistem: Masukkan lane perangkat lunak baru untuk mengeksekusi Service Task.

Quality Control

Checklist Kepatuhan Notasi To-Be

  • Tidak ada Sequence Flow yang menyeberangi dinding batas Pool.
  • Seluruh cabang Exclusive Gateway diberi label kondisi (*Success* vs *Failed*).
  • Seluruh nama task berformat aktif ([Kata Kerja] + [Objek]).

"Desain bukan hanya tentang bagaimana tampilan luarnya. Desain adalah tentang bagaimana sistem tersebut bekerja melayani pengguna."

— Steve Jobs

Contoh Kuantifikasi Hasil Redesign To-Be

Sebelum Redesign (As-Is)

- Total Langkah: 16 Task manual
- Waktu Siklus: 4 Hari (96 Jam)
- Waktu Kerja Nyata (VA): 2 Jam
- Efisiensi (PCE): 2.08%

Sesudah Redesign (To-Be)

- Total Langkah: 6 Task terotomasi
- Waktu Siklus: 15 Menit (0.25 Jam)
- Waktu Kerja Nyata (VA): 12 Menit (0.2 Jam)
- Efisiensi (PCE): 80.00%!

Kuis Evaluasi • Soal 1/4

Apakah tujuan utama dari penyusunan diagram proses bisnis To-Be?

A. Merekam kebiasaan buruk staf operasional yang sedang berjalan saat ini.
B. Merancang cetak biru alur kerja masa depan yang telah dioptimasi, bebas NVA, dan didukung teknologi informasi.
C. Menambah jumlah lembar formulir fisik yang wajib dicetak di kantor.

Pembahasan: B

Model To-Be adalah cetak biru kondisi masa depan yang diinginkan. Tujuannya adalah mengeliminasi inefisiensi yang ditemukan pada model As-Is dan menyuntikkan solusi otomatisasi TI.

Kuis Evaluasi • Soal 2/4

Tanda grafis apakah yang menandai bahwa suatu Task dieksekusi otomatis oleh sistem komputer (Service Task)?

A. Ikon sepasang roda gigi (Gears) di pojok kiri atas kotak task.
B. Ikon orang tersenyum di pojok task.
C. Garis ganda bergelombang di bagian bawah kotak.

Pembahasan: A

Menurut standar BPMN 2.0 resmi OMG, Service Task ditandai dengan ikon roda gigi (*gears*), yang menunjukkan bahwa tugas tersebut dijalankan oleh komputer tanpa campur tangan manusia.

Kuis Evaluasi • Soal 3/4

Mengapa tabel Gap Analysis sangat penting disajikan sebelum menampilkan diagram To-Be?

A. Agar laporan tugas terlihat memiliki jumlah halaman yang tebal.
B. Untuk memberikan pertanggungjawaban logis mengenai jurang masalah yang diselesaikan dan solusi TI yang dibutuhkan.
C. Untuk memecat karyawan yang tidak menguasai komputer.

Pembahasan: B

Gap Analysis berfungsi sebagai jembatan pembuktian. Tabel ini menunjukkan secara transparan mengapa perubahan diusulkan, masalah apa yang dilenyapkan, dan software apa yang wajib diadakan.

Kuis Evaluasi • Soal 4/4

Membatalkan pesanan belanja jika pembeli tidak mentransfer dalam 15 menit dimodelkan menggunakan simbol apa?

A. Boundary Timer Event (Lingkaran jam ganda yang menempel di sisi kotak task).
B. Start Message Event.
C. Data Store Reference.

Pembahasan: A

Kondisi *time-out* yang membatalkan atau menginterupsi aktivitas yang sedang berlangsung dimodelkan menggunakan Boundary Timer Event yang ditempelkan pada batas tepi task tersebut.

Tanya Jawab Analis 1

"Pak, apakah pada diagram To-Be seluruh aktivitas kasir harus digantikan oleh komputer?"

Tidak harus seluruhnya. Tujuan utama To-Be adalah mengotomatisasi pekerjaan yang bersifat mekanis dan membosankan (seperti menghitung uang kembalian dan mengecek kuitansi bank). Aktivitas yang membutuhkan keramahan manusiawi, penyambutan pelanggan, atau penjelasan produk tetap dipertahankan sebagai User Task.

Tanya Jawab Analis 2

"Bagaimana jika kami tidak menguasai bahasa pemrograman spesifik untuk modul TI yang diusulkan?"

Sebagai Systems Analyst, tugas utama Anda di mata kuliah ini adalah merancang spesifikasi dan arsitekturnya, bukan menulis baris kodenya. Anda cukup mendefinisikan: "Sistem ini membutuhkan Payment Gateway API dengan webhook callback dan database PostgreSQL di cloud". Spesifikasi itulah yang akan dieksekusi oleh tim programmer murni di dunia kerja nanti.
